# 一页纸 PRD：反馈入口与坏案例台账

**状态**：✅ 已上线实现（2026-11-27，见 `src/feedback.py`、`app.py`、`scripts/triage_feedback.py`），待外部用户试用验证　|　**版本**：v0.2（2026-11-27）　|　**来源**：[backlog-rice.md](backlog-rice.md) RICE 第 1 名（300）

本文件说明「为什么现在做反馈闭环」「做成什么样算成功」「明确不做什么」，以及它在什么条件下应该被判定为失败。

---

## 1. 一句话

在每次问答后加**一次点击**的反馈入口，把反馈汇成每周归类的坏案例台账——让「系统变好」第一次有真实用户信号，而不是只有我一个人的判断题。

## 2. 问题（为什么是现在）

- **现状**：整个仓库没有任何反馈入口（`app.py` / `src` 里 `反馈`、`thumb`、`feedback` 零命中）。所有质量结论都来自离线评测。
- **后果**：离线指标涨了，没人知道用户是否因此更信任它；离线指标没动，也不知道用户实际卡在哪一步。
- **已有的基础**（所以这件事很便宜）：失败分类已经做得很细——检索漏、生成漏项、过度保守、引用错、**度量口径误判**。台账直接复用这套分类，不需要发明新语言。
- **不做的代价**：每加一个功能，验证成本都是一次冷检索 208 秒的离线跑批；而用户真正的卡点可能根本不在这条链上。

## 3. 目标用户与场景

⚠️ **本节是假设，不是调研结论**——项目尚未做过用户访谈或可用性测试。

- **用户**：做材料选型、标准合规、人体尺寸推导的设计师与设计学生。
- **触发时刻**：他们在**把答案用于决定之前**，会先判断「这答案能不能信」。反馈入口要长在这个判断发生的那一刻，而不是事后发问卷。
- **反例**：如果入口放在页面底部、或者要求先填表，就等于没做——这一点写进验收判据（§4 护栏）。

## 4. 成功判据

| 类型 | 指标 | 本阶段目标 | 怎么算 |
| --- | --- | --- | --- |
| **北极星** | 每周**可归因的**坏案例数 | ≥ 5 条/周，其中 ≥ 3 条能落到具体机制 | 台账中 `status=已归类` 的条目 |
| 过程 | 反馈提交率 | ≥ 15% 的问答至少一次反馈 | 有反馈的会话 / 总会话 |
| 过程 | 归类时效 | 48 小时内 100% 完成归类 | 台账时间戳 |
| 护栏 | 用户负担 | 平均 ≤ 1 次点击，且不打断答案阅读 | 交互步骤计数 |
| 护栏 | 隐私 | 不采集 PII；问题原文可由用户选择不上传 | 数据字段审计（§6）|

### ⚠️ 样本量先说清

12 周、约 300 次问答、5 个用户，**不足以做显著性检验**。
本阶段的结论只能是**描述性**的：「这 5 个人里有 3 个在"证据条数不足"那一步放弃」可以写；
「满意度 82%」不能写。这条沿用项目自己的判据——分母不成立时，不报比率。

## 5. 范围

**做**

1. 反馈入口：点赞 / 点踩 + 可选「哪条证据不对」（勾选具体引用编号）
2. 台账：一条记录一个 JSON 行，字段见 §6
3. 每周归类模板：按 §7 的分类法归因，写处置结论
4. 通路：确认的坏案例进入离线回归集（让下一轮评测**自动**覆盖它）

**不做（本阶段）**

- ❌ 用反馈自动改答案、自动降级——反馈进台账，不进生成链路
- ❌ 人审队列、多用户账号与权限
- ❌ 反馈驱动的模型微调

> 明确写「不做」是 PRD 的一半：否则「用户点踩之后呢」会变成一个没人负责的悬空需求。
> 本阶段点踩的唯一后果是**每周多一条被归类的记录**。

## 6. 交互与数据

**用户看到什么**：答案下方两个按钮（👍 / 👎）。点 👎 后展开一行可选项：勾选「哪条证据不对 / 答案是编的 / 没回答我的问题 / 其他」，可留一句话。**不弹窗、不跳页、不阻断阅读。**

**我们记录什么**

| 字段 | 用途 | 必填 |
| --- | --- | --- |
| `session_id` / `question_id` | 关联到这次问答 | ✅ |
| `question_hash` / `answer_hash` | 允许不复述原文就能去重与追踪 | ✅ |
| `verdict` | `up` / `down` | ✅ |
| `reason_code` | 四选一（见上） | 👎 时必填 |
| `blamed_evidence_ids` | 用户指认的证据编号 → 直接指向检索还是生成 | 可选 |
| `free_text` | 用户自己的话（最有价值，也最难归类） | 可选 |
| `generator_backend` / `latency` / `evidence_count` | 复现这条反馈所处的配置 | ✅ 自动 |
| `snapshot_id` | 定位到哪个索引快照 | ✅ 自动 |

⚠️ **自动字段比用户填的字段更重要**：没有 `snapshot_id` 和 `backend` 的反馈，两周后无法复现。

## 7. 坏案例分类法（复用已有发现）

| 代号 | 定义 | 已有实例 | 处置 |
| --- | --- | --- | --- |
| `R1` 检索漏 | 需要的来源没进上下文 | 16 条任何深度都检不到的来源 | 开需求（切片/角色标签）|
| `R2` 排序错 | 来源进了上下文但排在截断之后 | k10 首目标来源排第 4 | 开需求（先验/权重）|
| `G1` 生成漏项 | 提到了类别或概念，没给出具体项与数值 | `坐姿膝高`、`680~760` | 提示词 / 契约收紧 |
| `G2` 过度保守 | 证据在包里，仍以「资料不足」收尾 | r17 h2 | 提示词加反向约束 |
| `G3` 引用错 | 引用编号不可解析，或引了不支持的来源 | 交付闸门已修 8 处 | 回归集 + 闸门 |
| `M1` 度量口径误判 | **不是系统错，是判据错** | `反推` vs `反算` | 修判据，且**要记录**，否则会误判成能力问题 |
| `U1` 问法歧义 | 问题本身有歧义，正确行为是澄清 | 「多大容量」未指定人群 | 检查澄清行为是否触发 |

`M1` 这一类是这份台账和普通「用户反馈表」最大的区别：**把"用户说的"和"判据算的"分开归因**，否则每一次降级都会被记成一次系统失败。

## 8. 风险与取舍

| 风险 | 处置 |
| --- | --- |
| **反馈偏差**：只有不满的人才点 | 用隐式信号交叉验证——重问率、会话时长、复制答案的比例 |
| **点踩率低 ≠ 系统好** | 预登记：提交率 < 5% 时**先怀疑入口设计**，不怀疑质量 |
| **归因污染**：用户说「证据不对」其实是判据错（`M1`）| 台账强制二选一：系统失败 / 判据问题 |
| **隐私** | 默认只存哈希 + 用户可选是否上传原文 |

## 9. 上线与验证

- **谁**：5 位设计学生（同学 / 实验室），任务式使用——让他们问**自己真实的设计问题**
- **问题从哪来**：[question-intake.md](question-intake.md) 的两阶段采集（阶段 1 **无提示**，
  否则收到的题会偏向库里已有的资料，缺口统计就成了循环论证）
- **多久**：2 周收集 + 1 周归类
- **可证伪的判据**：若 2 周内真实坏案例 **< 3 条**，判定为**入口设计失败**（而不是「系统已经够好」），先改入口再谈改进
- **反向信号**：若点踩集中在同一个 `reason_code`，说明问题不在个体而在机制 → 直接开需求，不走台账

## 10. 未决问题（需要拍板）

1. 问题原文默认上传还是默认只传哈希？（隐私 vs 可归因性）—— 建议默认哈希，用户可选明文
2. 坏案例进回归集的门槛：1 条就进，还是 ≥ 2 条？—— 建议 1 条即进，但标记「单次观测」，避免把噪声变成永久判据
3. 反馈入口是否出现在**拒答**的回答上？（拒答时用户最该被问「你认为这里真的没有资料吗」）—— 建议出现，且这是最高价值的一条反馈
